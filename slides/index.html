GP.02

Cadrage & Priorisation

Cadrage minimal

  • Vision en 1 phrase
  • 3 objectifs et 3 non-objectifs
  • Definition of Done claire

Priorisation rapide

  • Must : indispensable a la demo
  • Should : utile si temps disponible
  • Could : bonus
Backlog v0 (exemple Flipper)
MUST   - Physique bille + flippers
MUST   - Synchroniser 3 ecrans
SHOULD - Scores temps reel
COULD  - Mode multijoueur

Definition of Done
- Issue liee
- PR relue
- Doc mise a jour
ANTI-PATTERN

Tout demarrer en parallele sans ordre de priorite = retard garanti.

GP.03

Planification & Risques

Planification legere

  1. Choisir 2-3 objectifs pour la sequence
  2. Transformer en issues actionnables
  3. Fixer un responsable par issue
  4. Revue d'avancement courte et reguliere
CADENCE

Un point de 10 minutes vaut mieux qu'une reunion de 1 heure trop tard.

Registre des risques (simple)

Risque: specs floues
Probabilite: haute
Impact: fort
Signal: retours contradictoires
Action: valider DoD avant dev

Risque: conflit long sur main
Probabilite: moyenne
Impact: fort
Action: PR plus petites
RESULTAT ATTENDU

Moins de surprises, plus de decisions explicites, execution plus fluide.

J1.10

UML : c'est quoi ?

Unified Modeling Language

Un langage visuel et standardise pour decrire, concevoir et documenter un systeme logiciel.

  • Ne en 1997 (Booch + Rumbaugh + Jacobson)
  • Norme ISO/IEC 19505
  • Version actuelle : UML 2.5
CE QUE C'EST

Un vocabulaire commun pour que toute l'equipe parle la meme langue.

CE QUE CE N'EST PAS

Ni du code, ni un outil, ni une methode de gestion de projet.

STRUCTURE (ce que le systeme EST)

Diag. Use Case

Elements

  • Acteur (bonhomme) : qui utilise le systeme
  • Use case (ellipse) : une fonctionnalite
  • Systeme (rectangle) : le perimetre
  • Association (trait) : qui utilise quoi

Relations avancees

  • <<include>> : UC obligatoirement inclus
  • <<extend>> : UC optionnel
  • Generalisation : acteur herite d'un autre

  usecase "Configurer table" as UC5
  usecase "S'authentifier" as Auth

  UC1 ..> Auth : <<include>>
  UC5 ..> UC1 : <<extend>>
}

U --> UC1
U --> UC2
U --> UC4

@enduml
J1.14

Diag. de Sequence

Elements

  • Participant : un composant (acteur, UI, API, DB...)
  • Ligne de vie : duree d'existence (pointille vertical)
  • Message : appel (fleche pleine ->)
  • Retour : reponse (fleche pointillee -->)

Fragments

  • alt — si / sinon (branchement)
  • opt — optionnel
  • loop — repetition
@startuml
actor User as U
participant "UI" as UI
participant "API" as API
participant "DB" as DB

U -> UI : clique "Nouvelle partie"
UI -> API : startGame()
API -> DB : INSERT game
DB --> API : game created
API --> UI : 200 OK
UI --> U : affiche "Ready"

alt table non calibree
  API --> UI : erreur calibration
  UI --> U : "Calibrez la table"
end
@enduml

J1.23

Pourquoi les branches ?

Sans branches

main: A---B---C---D---E
           ^       ^
           |       |
         Alice   Bob (conflit!)
  • Tout le monde se marche dessus
  • Pas de review possible
  • Code casse en permanence

Avec branches

main:    A---B-------M
              \     /
feature:  C---D---E
              (review, puis merge)
  • Chacun travaille en isolation
  • Review avant merge
  • main reste stable
PRINCIPE

Une branche = un sujet isole. On merge quand c'est pret et valide.

J1.24

Strategies de branching

GitHub Flow

main + feature branches

  • Simple, 1 branche longue
  • PR + review pour merger
  • Deploy depuis main

Ideal pour nous

GitFlow

main + develop + features + releases

  • Complexe, multi-branches
  • Separe dev / staging / prod
  • Releases planifiees

Gros projets, releases rares

Trunk-based

Branches tres courtes (< 1 jour)

  • Merge continu vers main
  • Feature flags si besoin
  • CI/CD solide obligatoire

Equipes avancees, deploy continu

J1.25

Anatomie d'une bonne PR

Les ingredients

  • Titre clair : ce que ca fait
  • Issue liee : Fixes #12
  • Description : pourquoi + comment
  • Petit perimetre : 1 sujet = 1 PR
  • Commits propres : lisibles et atomiques
TAILLE IDEALE

< 200 lignes changees. Au-dela, la review perd en qualite.

Exemple de description

## Description
Ajout de la section architecture au CDC

## Issue liee
Fixes #7

## Changements
- Section 4 dans docs/cdc-technique.md
- Composants principaux + interactions

## Comment relire
1. Verifier coherence avec la vision
2. Verifier le format (structure CDC)
3. Composants realistes ?
J1.26

Culture de review

Quoi verifier ?

  1. Clarte : je comprends le but ?
  2. Coherence : ca colle avec l'existant ?
  3. Completude : rien ne manque ?
  4. Format : conventions respectees ?
  5. Perimetre : pas de bruit / hors-sujet ?
REGLE D'OR

Critiquer le code, jamais la personne.

Bon vs mauvais commentaire

MAUVAIS

"C'est nul, ca marchera jamais"

"Tu as pas compris le sujet"

BON

"Ce scenario ne couvre pas le cas ou la table n'est pas calibree. Tu veux l'ajouter en extension ?"

"Le nommage du fichier devrait suivre notre convention UC-XX.md"

J1.27

Merge : les options

Merge commit

*   Merge PR #3
|\
| * feat: add UC-03
| * docs: update vision
|/
* (main)

Garde tout l'historique. Cree un commit de merge.

Squash & merge

* feat: add UC-03 (#3)
* (main)

1 PR = 1 commit sur main. Historique propre.

Recommande pour nous

Rebase & merge

* docs: update vision
* feat: add UC-03
* (main)

Lineaire, mais reecrit l'historique. Avance.

J2.13

Do / Don't

DO
  • Petites PR, frequentes
  • Review systematique (meme sur docs/uml)
  • Ecrire le besoin avant le diagramme
  • Resoudre conflit en equipe (pas en solo)
  • main = stable, toujours
DON'T
  • Push direct sur main
  • Branches qui vivent 3 jours
  • PR enormes "tout le projet"
  • Commits "update" / "fix" sans contexte
  • Diagrammes "pour faire joli" non relies a un use case

Sprint CDC technique

DO

Assembler le CDC

  1. Compiler toutes les sections dans docs/cdc-technique.md
  2. Completer les sections manquantes (archi, stack, risques, roadmap)
  3. Verifier la coherence globale

LIVRABLE

PR "CDC technique v1" mergee sur main

PRESENTATION

10 min par equipe. Montrez votre CDC complet.

  • Tests de libs / frameworks
  • Benchmarks performance
  • Explorations documentees
